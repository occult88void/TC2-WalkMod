# ANALYSIS 10: PE debug identity и путь к символам TheCrew2.exe

Дата: 2026-11-17  
Источник: загруженный `/mnt/data/TheCrew2.exe`, PE headers и debug directory; локальная проверка файлов проекта.

## Цель

Проверить, есть ли у исследуемого EXE CodeView/PDB identity, которая позволит искать точный matching PDB, и уточнить, какие части машинного кода доступны в файле без запуска игры.

## 1. CodeView запись указывает точный PDB

В PE debug directory обнаружена запись типа CodeView (RSDS):

- Debug Directory RVA: `0x05C8EF10`
- Debug Directory size: `0x54`
- RSDS record file offset: `0x019642C0`
- RSDS record size: `0x6C`
- PDB path, записанный в EXE:  
  `D:\Projects\TC2\Version\PatchQ\Applications\Game\Bin\PC64\PC_WW\Master\TheCrew2.pdb`
- PDB GUID: `731ed9e1-c2e7-4727-9e93-5907d86d0ef1`
- PDB Age: `2`
- GUID без дефисов + Age (lookup key): `731ED9E1C2E747279E935907D86D0EF12`

Это точная идентичность ожидаемого PDB для данной сборки EXE. Одного имени `TheCrew2.pdb` недостаточно: найденный GUID и Age нужны, чтобы не перепутать символы от другой версии игры.

## 2. Где находится машинный код в PE

Извлечены заголовки 11 PE sections. Важные записи:

| Section | RVA | Virtual size | Raw pointer | Raw size |
|---|---:|---:|---:|---:|
| `.text` | `0x1000` | `0x29B8CEC` | `0` | `0` |
| `.rdata` | `0x29BA000` | `0x94B912` | `0` | `0` |
| `.data` | `0x3306000` | `0x6BFB18` | `0` | `0` |
| `.pdata` | `0x39C6000` | `0x2DBA24` | `0` | `0` |
| `.xcode0` | `0x3CA6000` | `0x684F87` | `0` | `0` |
| `.xcode1` | `0x432B000` | `0x1C427A8` | `0x800` | `0x1C42800` |

Следствие: обычные raw bytes секции `.text` в предоставленном файле отсутствуют. Это подтверждает ограничение предыдущего статического исследования: нельзя просто открыть этот EXE в дизассемблере и получить полный обычный код из raw `.text`.

Секция `.xcode1` физически присутствует в файле, но сама по себе её высокая энтропия/нестандартная раскладка не раскрывает native-функции. Без подтверждённого формата преобразования нельзя объявлять её содержимое распакованным кодом или самостоятельно подбирать декодирование.

## 4. Что это меняет в расследовании Player → Avatar

Найденный PDB identity сам по себе не раскрывает:
- реализацию `CMissionAtomGetLocalPlayer`;
- реализацию `CMissionAtomGetCurrentPlayer`;
- entity factory/registry;
- назначение current/controlled entity;
- runtime handoff между транспортом и Avatar.

Но теперь есть точный способ проверить, подходит ли найденный где-либо PDB к данной сборке. Если появится PDB с тем же GUID и Age, он потенциально позволит перейти от косвенных RVA и неполных дизассемблированных окон к именованным native-функциям и типам.

## 5. Следующий безопасный шаг

1. Искать matching PDB только по точной паре GUID + Age, а не по имени файла.
2. Проверять происхождение файла и соответствие сборке, не подменяя его PDB от другой версии.
3. Если matching PDB недоступен, искать документированные/легитимно полученные symbol artifacts или полные статические дампы кода этой же сборки.
4. После получения символов начать с реализаций `GetLocalPlayer` и `GetCurrentPlayer`, затем проследить вызовы к entity registry/factory и setter текущей управляемой сущности.
5. Не возвращаться к DLL hooks, in-process patching или обходу integrity checks: предыдущий тест уже показал, что такой путь вызывает предупреждение целостности.

## Вывод

У EXE обнаружена валидная CodeView RSDS-запись с точным PDB GUID `731ed9e1-c2e7-4727-9e93-5907d86d0ef1` и Age `2`. Сам PDB в доступных материалах отсутствует. Это не решает Player → Avatar handoff, но превращает поиск символов в точную задачу сопоставления конкретного PDB с конкретной сборкой, а не в поиск файла с похожим названием.

До получения matching symbols native-мост `Local Player → runtime Avatar → controlled entity` остаётся неустановленным.
