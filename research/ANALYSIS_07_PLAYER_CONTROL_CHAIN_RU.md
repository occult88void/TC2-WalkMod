# Analysis 07: цепочка управления игроком и жизненный цикл транспорта

Дата: 2026-11-17  
Ветка: `analysis-07-player-control-chain`  
База: `analysis-05-native-lifecycle-ver09`

## Ограничения и безопасность

- Ветка создана отдельно от `main`; игровые DLL не менялись.
- Bootstrap 10 не использовать. В двух приложенных логах (HQ Rally/GP и House) есть `PROBE_FINGERPRINT_OK`, затем `PROBE_ABORT code signature mismatch; no hooks installed`. Следовательно, эти два запуска не содержат наблюдений от установленных хуков.
- Пользователь отдельно сообщил о предупреждении игры `File Corrupted!` при наличии DLL. Это достаточная причина не продолжать инъекционные эксперименты и не пытаться обходить проверку целостности.
- Все выводы ниже сделаны офлайн по уже существующим бинарным окнам v09. Нового чтения памяти игры не проводилось.

## Подтверждённые наблюдения

### 1. RVA 0x204800: update/coordinator, не установленный обработчик Leave

Вход:
- RCX сохраняется как основной объект (`this`) в RDI.
- XMM1 копируется в XMM10 и используется как delta при уменьшении float-поля `[rdi+0xE0]`. Это сильный признак update/tick-процедуры.
- Через `[rcx+0x28]`, затем `[+0x18]` получается связанный объект.
- Вызов `0x11DDA0` возвращает объект, из которого читается поле `+0x568`.

Управление:
- В процедуре многократно читается глобальный слот RVA `0x343C630`.
- Используются поля менеджероподобного объекта `+0x1DD8`, `+0x1DE8`, `+0x1E68`.
- Проверяется состояние `[rsi+0x170] == 2`.
- Ветки обращаются к selector bytes `+2` и `+0x23) в объекте по `manager+0x1DE8`, затем выбирают указатель из таблицы `manager+0x1DD8`.
- При одной из ветвей проверяется таймер `[rdi+0xE0]`, затем вызывается `0x1FA530) (call site `0x204C86`) и очищается byte `[rdi+0xE4]`.
- Другая ветвь вызывает `0x1FA430) (call site `0x204CA9`).
- При отсутствии активной ссылки `[r15+0x568]` процедура вызывает cleanup `0x841100) (call site `0x204CE5`).

Интерпретация:
- Процедура координирует жизненный цикл vehicle/replica в avatar-related режиме и периодически обновляет состояние.
- Нельзя называть её Leave handler: в доступном окне нет доказательства обработки пользовательской кнопки или переключения на пешего игрока.
- Захват заканчивается на RVA `0x204E00`, посреди процедуры. Ветки на `0x205107`, `0x205313`, `0x205379`, `0x2053E2` не захвачены. Поэтому control-flow graph неполный.

### 2. RVA 0x1FA430: cleanup/destroy часть vehicle-avatar режима

- Проверяет связанные объекты через `[rcx+0x28]` и `[+0x18]`.
- При валидной ветви вызывает `0x841100).
- Устанавливает byte `[rdi+0x54] = 1`.
- Функция целиком помещается в доступные 0x180 байт и заканчивается около RVA `0x1FA52A`.

Это подтверждает cleanup/state transition в соответствующем объекте. Само по себе не доказывает удаление исходной машины игрока или создание пешего персонажа.

### 3. RVA 0x1FA530: replica-vehicle path, но окно обрезано

- Использует связанный объект из `[rcx+0x28]` и объект из `[rcx+0x18]`.
- Проверяет поля `+0x6A8`, `+0x698`, `+0x568) и данные через менеджерную таблицу.
- При некоторых условиях вызывает cleanup `0x841100), затем virtual method по смещению `+0x238).
- Читает selector byte `manager[+0x1DE8]+3`, выбирает объект через `manager[+0x1DD8]), затем получает поле `+0xDF8) и вызывает `0x796CC0) либо `0x796C70).

Это согласуется с выбором/созданием/обслуживанием реплики транспортного объекта. Но доступный дамп заканчивается на RVA `0x1FA6B0`, то есть в середине процедуры. Фактическая ветка создания и её последующие вызовы не видны. Нельзя утверждать, что мы уже нашли универсальную фабрику транспорта.

### 4. RVA 0x841100 и 0x841780: подтверждённая очистка связанной сущности

`0x841100`:
- Берёт `rbx = [rcx+0x568]`.
- Вызывает `0x841780`.
- Если `rbx != 0`, выбирает manager table entry по selector byte `+3) и передаёт объект в `0x4EC7B0).

`0x841780`:
- Берёт `rbx = [rcx+0x568]`.
- Сравнивает его с объектом из manager table, выбранным selector byte `+4).
- Вызывает методы/процедуры очистки, включая `0x4FB0C0`, `0x76D1B0`, и при совпадении дополнительный путь `0x613090).
- В конце обнуляет `[rdi+0x568]` и `[rdi+0x570]`.

Поля `+0x568` и `+0x570` являются ссылками/состояниями, которые cleanup снимает. Их точные классы и семантика пока не доказаны.

### 5. Manager candidate

Связь к глобальному слоту RVA `0x343C630` и обращения к `+0x1DD8/+0x1DE8/+0x1E68` подтверждены несколькими функциями. Внутри процедуры реально читаются selector bytes и индексируется таблица указателей. Это уже не случайное совпадение адресов.

Однако название класса менеджера остаётся неизвестным. Рабочее обозначение: manager candidate / lifecycle manager. Нельзя пока называть его Player Manager.

## Что это меняет в поиске

Главная новая зацепка — не отдельная функция spawn, а общая машина состояний вокруг avatar-mode и replica-vehicle:
1. update-процедура выбирает объект через manager selector table;
2. создаёт или поддерживает replica-vehicle path;
3. очищает связанный объект через `0x841100/0x841780`;
4. состояние привязано к объекту с полями `+0x568/+0x570).

Это полезная половина жизненного цикла, но пока только транспортная/аватарная сторона. Нет доказанного участка, где:
- создаётся `CITEntityAvatarTC2` или `CITEntityAvatarInterior` как управляемый локальный персонаж;
- назначается local player / possession target;
- подключаются input и camera;
- сохраняется исходный vehicle и выполняется обратный переход.

2. **Разобрать связанные функции по call targets**: `0x11DDA0`, `0x8E4D60`, `0x8DA550`, `0xAFD5C0`, `0x76DED0`, `0x796CC0`, `0x796C70`, `0x4EC7B0`, `0x613090`. Их назначение пока выводится только из контекста вызовов.
3. **Сопоставить lifecycle manager с entity/archetype data**: искать имена типов и компонентов, чьи layout/методы согласуются с selector table и replica vehicle.
4. **Отдельно искать Leave/input chain** через штатные миссионные действия и HQ/Housing exit handlers. Не переименовывать найденный update в обработчик кнопки без xref/доказательства.
5. **Только после обнаружения полного перехода** проектировать вызов штатного пути или недостающую реализацию. Не добавлять DLL-хуки ради сбора данных.

## Уровни уверенности

- Высокая: конкретные инструкции, смещения полей, вызовы и переходы, которые находятся внутри захваченных окон.
- Средняя: интерпретация процедуры как avatar-mode/replica-vehicle lifecycle по структуре ветвей и названиям, присвоенным в предыдущем исследовании.
- Низкая/не установлено: точные имена классов менеджера, семантика selector bytes, конкретный player controller, обработчик Leave, camera/input handoff, универсальный spawn.
