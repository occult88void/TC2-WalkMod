# Предварительный разбор нативной цепочки жизненного цикла

## Идентификация сборки

Снимки кода в `TC2_runtime_capture.zip` были получены из процесса с:

- PE timestamp: `0x68D1CFB8`;
- SizeOfImage: `0x05F94000`;
- AMD64.

Переданный `TheCrew2.exe` имеет те же значения в PE-заголовке. Это подтверждает совпадение fingerprint сборки по двум полям. Полное равенство EXE-файла и runtime-образа этим не доказывается.

## Основная зацепка: update-like routine

В архиве присутствует runtime-окно по RVA `0x204800`, файл:

`avatar_vehicle_lifecycle_caller_rva_2115584.bin`

Размер старого окна — `0x600`. Это не полная функция: внутри есть ветви на адреса вплоть до `0x205379` и `0x2053E2`, выходящие за пределы захвата.

По дизассемблированию подтверждается:

1. Windows x64 ABI: `RCX` сохраняется как `this`, `XMM1` сохраняется в `XMM10`.
2. `XMM1` далее используется как delta-time: в ветке около RVA `0x204C44` значение вычитается из float-поля `[this+0xE0]`, результат записывается обратно.
3. В одной ветке функция вызывает RVA `0x1FA530` (вызов около `0x204C86`), после чего записывает ноль в байт `[this+0xE4]`.
4. В другой ветке функция вызывает RVA `0x1FA430` (вызов около `0x204CA9`), если байт `[this+0x54]` равен нулю.
5. В той же функции используется объект, полученный через вызов RVA `0x11DDA0`; из него читается поле `+0x568`.
6. Вызов cleanup-кандидата RVA `0x841100` встречается также в этой update-like routine.

**Вывод высокой уверенности:** RVA `0x204800` — периодически вызываемая update-процедура или близкий к ней обработчик, который использует delta-time и переключает между двумя ветвями с вызовами `0x1FA530` и `0x1FA430`.

**Пока не доказано:** что эти ветви непосредственно переключают локального игрока между автомобилем и пешим аватаром. Названия из старых capture-файлов — метки исследователя, не символы из PDB.

## Две ветви

### RVA 0x1FA430

Захваченное окно `destroy_current_vehicle_avatar_mode_rva_2073648.bin` имеет размер `0x180`. Основные наблюдения:

- читает `[this+0x28]` и вложенный указатель `[...+0x18]`;
- читает объект из `[this+0x18]`;
- получает дважды некий descriptor-like объект через виртуальный вызов `[vtable+0x08]`;
- сравнивает поля descriptor-like объекта с глобальными значениями;
- при прохождении проверок вызывает `0x841100` с объектом из `[this+0x18]`;
- устанавливает байт `[this+0x54] = 1`.

Это доказывает связь процедуры с очисткой/снятием состояния и флагом `+0x54`, но не доказывает, что очищается именно автомобиль или пеший аватар.

### RVA 0x1FA530

Захваченное старое окно `spawn_replica_vehicle_rva_2073904.bin` имеет размер `0x180` и обрывается до конца логики. В видимой части:

- повторно использует `[this+0x28]` и `[this+0x18]`;
- проверяет байт `[nested+0x6A8]`;
- проверяет объект по `[object+0x568]` и сравнивает его поле `+0x10` с `[nested+0x698]`;
- в другой ветке вызывает cleanup-кандидат `0x841100`;
- вызывает виртуальную функцию по смещению `+0x238`;
- выбирает один из двух прямых call-target: `0x796CC0` или `0x796C70`, исходя из байта `[nested+0x6A8]`.

**Пока неизвестно:** что именно создают или активируют эти вызовы. Старое имя `spawn_replica_vehicle` не считать установленным.

## Cleanup-кандидаты

### RVA 0x841100

Начало короткой процедуры:

- читает указатель `[this+0x568]`;
- вызывает `0x841780`;
- если указатель существует, использует глобальный Component Host, selector и component table;
- вызывает несколько функций с объектом;
- обнуляет `[this+0x568]` и `[this+0x570]`.

### RVA 0x841780

Внутренняя процедура:

- повторно читает `[this+0x568]`;
- использует selector byte `+0x04` и соответствующую запись component table;
- вызывает несколько функций с объектом;
- при совпадении одного из полей с компонентом Host вызывает дополнительный callback;
- обнуляет `[this+0x568]` и `[this+0x570]`.

**Вывод средней/высокой уверенности:** эти процедуры очищают или отсоединяют связанный объект, хранящийся в поле `+0x568`, и синхронизируют это действие с компонентами Component Host. Тип объекта пока не установлен.

## Связь с Component Host

В старом двухсостоянийном снимке `capture_4116_22739453` один и тот же Host использовал:

| Поле Host | Freedrive | HQ |
|---|---:|---:|
| `+0x650` | `0x1F555FA5BD8` | `0x1F561389E08` |
| `+0x658` | `0x1F28010FDD8` | `0x1F28010FDD8` |
| `+0x680` | `0x10` | `0x18` |
| `+0x6D0` | `0x1F281147A50` | `0x1F286896740` |
| `+0x6D8` | `0x1F2AD579BF8` | `0x1F2AD579BF8` |
| `+0x700` | `0x1F` | `0x22` |

Эти значения не позволяют назвать объекты. Они лишь показывают, что две пары указателей имеют разную динамику: `+0x650` и `+0x6D0` меняются, а соседние `+0x658` и `+0x6D8` в данном снимке остаются одинаковыми.

### Прямая связь с нативной цепочкой

В дизассемблированных функциях найдено обращение к тому же глобальному слоту Host:

- глобальный указатель загружается по RVA `0x0343C630`;
- далее код читает `Host + 0x1DD8` как указатель на component table;
- читает `Host + 0x1DE8` как указатель на selector;
- в разных местах использует байты selector `+0x02`, `+0x03` и `+0x04` для выбора записи таблицы.

Эти обращения присутствуют в окнах `0x204800`, `0x1FA530`, `0x841100` и `0x841780`.

**Вывод высокой уверенности:** Component Host, который Bootstrap12 снимал в Freedrive и HQ, напрямую участвует в исследуемой нативной цепочке. Это уже не просто общий контейнер, случайно присутствующий в обоих состояниях. Конкретные роли выбираемых компонентов пока не установлены.

## Следующий шаг

Bootstrap13 собирает:

- расширенные окна `0x1FA430`, `0x1FA530`, `0x204800`, `0x841100`, `0x841780`;
- прямые call-targets из этих процедур;
- объекты и candidate-vtable для Host `+0x650`, `+0x658`, `+0x6D0`, `+0x6D8`;
- scalar values Host `+0x680` и `+0x700`;
- оба исходных состояния: Freedrive и HQ.

После получения снимка нужно:

1. восстановить полную логику update-like routine и двух ветвей;
2. определить реальные типы объектов по Host pointer fields;
3. сопоставить vtable targets с функциями жизненного цикла;
4. проверить, где именно меняется ссылка на локальную управляемую сущность.

До этих проверок не делать патчей и не утверждать, что найден переключатель Vehicle/Avatar.
