# Bootstrap15 — реализация и протокол runtime-сбора

## Статус

Реализация находится в `src/dinput8_proxy.cpp`. DLL собирается GitHub Actions под Windows x64. Это диагностический bootstrap, не мод свободной ходьбы и не реализация Leave.

Режим остаётся строго read-only:
- нет хуков;
- нет патчей кода;
- нет записей в память игры;
- нет вызова игровых функций;
- нет сценария Leave или открытого мира.

## Сценарии

1. Ctrl+Shift+F10 — Freedrive с транспортом.
2. Ctrl+Shift+F11 — HQ с пешим персонажем.

Каждый хоткей ожидается до 10 минут. После F10 DLL делает первый сбор и продолжает ждать F11. В логах завершение обозначается `BOOTSTRAP15_SEQUENCE_COMPLETE`.

## Что захватывается

### Host
- Host root до 0x4000 байт, если доступный регион памяти позволяет.
- Поля +0x650, +0x658, +0x6D0, +0x6D8 с раздельным захватом:
  1. wrapper;
  2. nested object по wrapper.qword0;
  3. true vtable по nested.qword0;
  4. исполняемые указатели, найденные в wrapper/nested object, с метками byte offset.
- Host +0x1E68 отдельно как объект с прямой vtable.
- Ссылки/флаги Host +0x538, +0x548, +0x5B8, +0x5C8.
- Области Host +0x2BC8, +0x2C08, +0x2D08 и значения их первых qword.
- Скаляры +0x680 и +0x700.

### Таблица компонентов
- Стабильные двойные снимки таблицы и селектора.
- Логическая карта selector offsets: 0x03, 0x11, 0x06, 0x1C, 0x23, 0x25, 0x1A, 0x1D, 0x22, 0x20, 0x08.
- Все валидные объекты таблицы получают базовый захват 0x400 и настоящую vtable.
- Логические компоненты 0x03 и 0x11 расширяются до 0x1800; 0x06, 0x1C, 0x23 — до 0x800. Фактический размер ограничен доступным регионом памяти.
- Для 0x03 исследуются внутренний адрес +0xF30 и wrapper по +0xDF8. Wrapper не трактуется как vtable: отдельно сохраняются его байты, code pointer fields, ссылки +0x98/+0xA8 и callbacks +0x18/+0x48/+0x78.
- Для 0x11 исследуется внутренний адрес +0x1258.
- Для внутренних адресов сохраняются как сами байты по адресу owner+offset, так и объект, на который указывает qword в этом месте, если указатель валиден.

### Нативный код
Сохраняются ранее изученные Bootstrap13 окна и дополнительные RVA, связанные с Host +0x6D0:
- 0xB2FF30, 0xB2FF50, 0xB2FAA0, 0xB2F430;
- 0xB77FA0, 0xB78010, 0xB948E0, 0xB78150;
- 0xB786A0, 0xB78710, 0xB96590, 0xE63E40, 0xECCEE0.

Каждая цель проверяется относительно PE fingerprint и executable section. Наличие адреса в объекте не считается доказательством, что он вызывается как виртуальный метод.

## Связь с точками появления

В игровых данных отдельно подтверждены архетипы:
- `CITEntityHeadQuarterCharacterSpawnPoint`
- `CITEntityHeadQuarterExitPoint`
- `CITEntityHousingCharacterSpawnPoint`
- `CITEntityHousingExitSpawnPoint`

Также известны mission atoms `CMissionAtomSpawn` и `CMissionAtomTeleportEntity`. Эти структуры относятся к данным/миссионному runtime. Bootstrap15 не парсит их определения и не доказывает, что mission Spawn/Teleport доступны из Freedrive. Задача DLL — собрать runtime Host/component references, которые могут связать состояние аватара, размещение и управление.

## Как провести сбор

1. Использовать собранный x64 `dinput8.dll` в той же конфигурации запуска игры, что использовалась для предыдущих bootstrap-сборов. Не обходить и не отключать античит.
2. Запустить игру и дождаться Freedrive с транспортом.
3. Нажать Ctrl+Shift+F10 один раз.
4. Перейти в HQ, где персонаж находится пешком.
5. Нажать Ctrl+Shift+F11 один раз.
6. Дождаться строки `BOOTSTRAP15_SEQUENCE_COMPLETE`.
7. Передать целиком каталог `TC2_runtime_capture/capture_*` и файл `TC2_Walkmod.log`, находящиеся рядом с исполняемым файлом игры.

Если F11 не нажат в течение 10 минут после F10, второй снимок не будет сделан. Если DLL не загружается, сначала проверить прокси-загрузку и лог, не добавляя новых сценариев.

## Как интерпретировать результат

Для сравнения Freedrive/HQ необходимо сопоставлять:
- одинаковые logical selector offsets, а не индексы таблицы;
- wrapper → nested → true vtable;
- значения Host +0x538/+0x5B8 и соответствующие внутренние адреса компонентов;
- object bytes и code pointer fields по смещениям;
- callbacks и прямые thunk targets.

Стабильное чтение подтверждает только неизменность байтов в момент двойного чтения. Оно не доказывает назначение объекта.

## Что Bootstrap15 не доказывает

- Что найден обработчик Leave.
- Что игра действительно телепортирует игрока при любом переходе.
- Что mission Spawn/Teleport можно вызвать из Freedrive.
- Что найден способ назначить пешего персонажа локальным управляемым игроком.
- Что точки появления можно динамически создавать или использовать вне HQ.
- Что свободная ходьба работает.

## Следующий этап

После анализа Bootstrap15 перейти к адресному поиску перехода и координат:
1. найти world transform транспорта и пешего аватара;
2. проверить, есть ли в runtime отдельная spawn transform/позиция;
3. определить операции регистрации локального/текущего игрока и передачи управления/камеры;
4. только затем сравнить штатный переход и оценить, можно ли воспроизвести его для динамической точки рядом с оставленным транспортом.

Bootstrap15 считается последним широким Host/component capture. Следующий сбор должен быть событийным и узким, а не ещё одной переписью всей памяти.
